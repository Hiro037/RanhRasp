# Предлагаемая архитектура RanhRasp

## 1. Что есть сейчас

Репозиторий совмещает несколько контуров:

- Telegram-бот на aiogram;
- FastAPI веб-интерфейс и HTTP API;
- SQLAlchemy модели и репозитории;
- парсер Word-файлов расписания;
- HTML/Jinja/Playwright генерацию PNG расписания;
- in-memory кэш изображений.

Функциональность полезная, но часть ответственности пересекается: бот напрямую вызывает репозитории, парсер напрямую знает о UnitOfWork, а генерация картинки зависит от глобального временного файла.

## 2. Целевая структура для VK-бота

```text
app/
  core/
    config.py          # переменные окружения, настройки БД, VK, админов
    logging.py         # единый формат логов
    clock.py           # дата/время и timezone
  domain/
    entities.py        # User, Group, Lesson как доменные DTO
    errors.py          # доменные исключения
  application/
    schedule_service.py
    user_service.py
    feedback_service.py
    import_service.py
    analytics_service.py
  infrastructure/
    db/
      models.py
      repositories.py
      unit_of_work.py
    rendering/
      html_renderer.py
      image_cache.py
    parsing/
      word_schedule_parser.py
      doc_converter.py
  adapters/
    vk/
      bot.py
      keyboards.py
      handlers.py
    telegram/
      bot.py           # временно оставить для совместимости
    web/
      api.py
      templates/
```

## 3. Принципы

1. **Бизнес-логика не зависит от VK/Telegram/FastAPI.** Платформенные обработчики только преобразуют входящие события в вызовы сервисов.
2. **UnitOfWork находится на границе application/infrastructure.** Сервисы получают UoW и не импортируют конкретный SDK бота.
3. **Рендеринг и кэш — отдельный инфраструктурный модуль.** Его можно заменить с Playwright на другой движок.
4. **Парсер не пишет в БД.** Парсер возвращает DTO, импорт-сервис решает, что удалять и создавать.
5. **Кнопки платформенно-независимы.** Сначала строится модель меню, затем адаптер превращает ее в VK keyboard или Telegram inline keyboard.
6. **Все настройки через config.** Никаких обязательных глобальных значений при импорте модуля.

## 4. Рекомендуемый путь миграции

### Этап 1. Стабилизация текущего кода

- Добавить безопасный `DB_URL` по умолчанию.
- Разделить параметры SQLAlchemy для SQLite и серверных БД.
- Починить кэш изображений по группе.
- Сделать временные HTML-файлы уникальными.
- Сделать импорт расписания идемпотентным.

### Этап 2. Выделение сервисов

- `ScheduleService`: получить расписание, сформировать текст, запросить PNG.
- `UserService`: создать/обновить пользователя, сохранить группу.
- `FeedbackService`: отправить отзыв администратору.
- `ScheduleImportService`: конвертировать, распарсить, удалить старые занятия, импортировать новые.

### Этап 3. VK-адаптер

- Реализовать входящие события VK.
- Реализовать VK keyboards.
- Подключить сервисы без копирования бизнес-логики из Telegram-бота.

### Этап 4. Production-ready

- PostgreSQL и Alembic как обязательный контур миграций.
- Redis для кэша изображений и FSM-состояний.
- Docker Compose для app + db + redis.
- CI: lint, type-check, unit-tests, миграции.

## 5. Что заменено как неэффективное

- Глобальный временный файл HTML заменяется уникальным временным файлом на каждый рендер.
- Очистка кэша по группе больше не пытается угадывать группу по хвосту md5-хэша.
- Кэш возвращает копию `BytesIO`, чтобы повторная отправка не зависела от позиции указателя.
- Повторный импорт расписания удаляет старые занятия за фактически затронутый диапазон дат.
- SQLite больше не получает параметры пула, которые предназначены для PostgreSQL/MySQL.
